1. Core Philosophy

The Workbench is a minimal, browser-based personal workspace designed for the corporate desktop user — the person on a locked-down ThinkPad who can't install apps but can open a browser tab.

It is not a replacement for email, spreadsheets, project management software, calendars, or accounting tools. It is the control surface above them.

The application helps the user:

• See what needs attention
• See what is happening soon
• See where they are in their projects
• See what information they need
• See what they haven't done recently
• Occasionally, remember to breathe and go live

The fundamental philosophy:

Work deserves focus.
Rest deserves permission.
Life deserves the remaining time.

The application should help the user finish work, rather than encouraging them to spend more time inside the application.

The final interaction is not "keep being productive." It's: "You're done. Close the browser."

───

2. Platform

Primary target: Browser-native web application for desktop.

Initial deployment:
• GitHub Pages
• Static hosting
• No installation
• No account
• No mandatory backend
• No server-side database

Desktop-only. No mobile responsiveness. Mobile users have plenty of productivity app options. The corporate desktop user has almost nothing that's personal and local-first. Desktop-only is not a limitation — it's the target audience.

Minimum viewport: 1024px width. Tested across Chrome, Edge, and Firefox.

Homepage instructions: The browser controls homepage/new-tab settings. The Workbench provides browser-specific instructions for making it the homepage, rather than attempting to change browser settings programmatically.

3. Technology Stack

Initial stack:
• HTML
• CSS (with CSS variables for theming)
• Vanilla JavaScript (ES modules, async/await)

No framework. No Vue. No Tailwind. The UI remains lightweight and understandable.

Optional library (Phase 5 only):

Key Architectural Decisions

1. One IndexedDB database, multiple object stores

Database: workbench
Version: 1

Stores:
  - tasks        (key: id, indexes: projectId, status, phaseId)
  - projects     (key: id, indexes: status)
  - phases       (key: id, indexes: projectId)
  - notes        (key: id, indexes: projectId, standalone)
  - sops         (key: id)
  - flowcharts   (key: id) — if kept
  - calls        (key: id, indexes: when, status)
  - emails       (key: id, indexes: when, status)
  - meetings     (key: id, indexes: when)
  - reminders    (key: id, indexes: due, status)
  - activities   (key: id, indexes: type) — for days-since
  - messages     (key: id) — quotes/human messages
  - settings     (key: key) — key-value store
  - meta         (key: key) — backup timestamps, version, etc.


2. Async data layer

Every data operation goes through store.js which wraps db.js. Widgets never touch IndexedDB directly.

3. Widget registration pattern

Each widget is a self-contained module with a standard interface:

js
export const widget = {
  name: 'calls',
  label: 'Calls',
  icon: '📞',
  
  async render(container) { ... },
  async refresh() { ... }
};


4. Simple hash-based routing

No router library. app.js handles hashchange events and maps routes to page modules.

5. Event delegation

One listener per widget container. Actions identified via data-action and data-id attributes. No per-element listeners that could leak.

6. CSS variables for theming

Light/dark themes via data-theme attribute on root element. All colors, spacing, and radii defined as CSS custom properties.

───

5. Data Architecture

Primary storage: IndexedDB, local to the browser.

Privacy philosophy: Private by default. Portable by design. The application does not require users to upload their personal/work information to any server.

Data durability:
• A dismissible backup banner appears every 3-4 days prompting the user to export a backup
• First-run warning explains that data lives in THIS browser only
• One-click export to workbench-backup.json
• meta store tracks last backup timestamp

No history, no archive. Completed tasks are offered for deletion, not stored in a "completed tasks" graveyard. The Workbench is a surface for today, not a record of your life.

6. Import / Export

Full backup:
Export Workbench
  → workbench-backup.json
  → Import on another device


Format:
json
{
  "format": "workbench",
  "version": 1,
  "type": "full-backup",
  "exportedAt": "2026-08-12T10:00:00Z",
  "data": { ... }
}


Version field allows future migration when the data model changes.

Selective sharing:
• SOP → bank-reconciliation.sop.json
• Flowchart → process.flow.json
• Note → meeting-note.note.json
• Project → month-end.project.json

Users can share individual pieces without exposing their entire Workbench.

  │    └── Task
  ├── Phase
  │    ├── Task
  │    └── Task

Task lifecycle:

• Completed
• Offered deletion (no archive, no history)
• Reopened if needed

The purpose: convert a vague mental model into something concrete. You aren't fighting "month-end." You're completing 3 remaining things.

9. Phases

Phases provide structure between a project and individual tasks.

Each phase contains:
• Tasks
• Status
• Notes
• Progress
• Relevant context

Example:
PHASE: RECONCILIATION
1 / 3 complete

Notes:
• Waiting for statement
• Two unclear transactions
• Confirm transfer with FM

Next action:
📞 Call Josh


Objective: Context preservation. A user should be able to leave a project for several days and return without reconstructing the entire mental model.

10. SOP

A dedicated area for procedures. Simple. Not a document-management platform.

Format: Titled steps with optional notes.

SOP: Bank Reconciliation

Step 1: Download statement from banking portal
Step 2: Match transactions against ledger
Step 3: Flag unmatched items
Step 4: Post adjustments
Step 5: Confirm closing balance


Capabilities:
• Create SOP
• Edit SOP
• Read SOP
• Organize SOP
• Export SOP (selective sharing)
• Import SOP

No rich text editor. No embedded images. No approval workflows. The Workbench SOP is a quick-reference card, not a document system.

19. Stress Buster

A tiny distraction mechanism. Maximum two minutes.

Available activities:

1. Kill a Mosquito — A mosquito buzzes around the screen. Click to swat it. Satisfying. Brief.
2. Smash Someone — A cartoon character appears. Click to smash. Cartoon violence, nothing graphic.
3. Pop Balloon/Bubble — Balloons or bubbles float across the screen. Click to pop. Simple, calming.
4. Love Them — See Section 20.

Rules:
• Maximum two minutes
• No leaderboard
• No achievement system
• No score chasing
• No skill required

The user should finish thinking: "Okay. Back to work."

26. UX Principle

Every widget follows:

LEVEL 1: See what matters.
    ↓
LEVEL 2: Click to understand.
    ↓
LEVEL 3: Take action.


Empty states are statements, not prompts.

Bad:
⚠️ No calls scheduled! Add one now?
[+ Add Call]


Good:
📞 CALLS
Nothing on the phone today.


No exclamation marks. No "add one now." Just a quiet statement of fact. The "+" button lives in the widget header as a small icon, always present.

Empty state language:


Widget
Empty State

Calls
Nothing on the phone today.

Emails
Nothing queued.

Meetings
Nothing on the calendar.

Reminders
All clear.

Tasks
Nothing pressing.



The widget stays visible. The user knows it exists. But it doesn't demand attention when there's nothing to demand attention about.

Browser

31. Workflow: Overseer & Code Generator

Process

1. Project Owner decides what to build next
2. Overseer (GLM 5.2) generates a detailed prompt for the specific file/module
3. Project Owner feeds the prompt to Gemini (code generator)
4. Gemini generates the code
5. Project Owner brings the code back to Overseer for review
6. Overseer reviews for correctness, security, consistency, and architectural alignment
7. Overseer provides feedback or approval
8. Project Owner integrates approved code

Prompt Generation Principles

When the Overseer generates prompts for Gemini, each prompt will specify:

1. The file being generated — exact path and filename
2. The interface — what functions/exports the module provides
3. The constraints — no external dependencies, vanilla JS modules, async/await
4. The data shape — object structure with all fields
5. The error cases — what to handle (DB failures, quota, private mode, empty data)
6. The architectural pattern — widget registration, event delegation, store layer access

Review Checklist

For every code review, the Overseer checks:

[  ] XSS safety — user inputs via textContent or escape function, never raw innerHTML
[  ] IndexedDB transaction correctness — transactions used before auto-commit, readwrite txs awaited with .done
[  ] Async consistency — all data functions use async/await, no mixed .then() patterns
[  ] Event delegation — no per-element listeners that could leak on re-render
[  ] Error handling — try/catch on all async operations, user-visible error states
[  ] Loading states — async fetches show loading indicator, not empty content
[  ] Empty states — statements, not prompts (per Section 26)
[  ] Architectural consistency — follows the patterns in Section 4
[  ] No scope creep — doesn't introduce features outside the plan
[  ] Desktop-only — no mobile responsiveness code

32. The Product's Real Value

The Workbench solves a very ordinary problem:

People carry too much of their work inside their heads.

The system externalizes:

• What needs doing
• Where a project stands
• What comes next
• What someone needs to be contacted about
• What a meeting is about
• Where an SOP lives
• What hasn't happened for a while

And then it adds something conventional productivity software forgets:

The person using it has a life.

That's why task progress, calls, emails, meetings, SOPs, days-since, weather, stress, love them, and after-hours reminders can coexist without feeling random.

They all serve one larger purpose:

Organize your work. Finish what matters. Then leave the screen and live.

33. Final Product Statement

The Workbench

A minimal browser-based workspace for organizing your day, keeping work out of your head, and making it easier to leave work behind.

It doesn't try to replace the tools you already use. It sits above them. It gives you one place to see your work, your context, your progress, and the small things that matter outside work.

No installation.
No mandatory account.
Local-first.
Portable.
Minimal.
Useful.
Human.

And the final interaction is not:

"Keep being productive."

It's:

"You're done. Close the browser." ❤️
